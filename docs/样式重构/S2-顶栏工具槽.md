## 2. 为什么要做：宽度预算

按现有 CSS 估算，顶栏在**最小窗口 960px**（`src-tauri/tauri.conf.json` 的 `minWidth`）下：

```
可用宽度 = 960 − 侧栏 240 = 720px

当前占用：
  padding 24 + 粒度段 94 + gap 8 + ‹ 24 + gap 8
  + anchor 标签 150（周粒度最长「2026年8月18日 – 8月24日」）+ gap 8 + › 24
  + gap 8 + 今天 48 + gap 8 + 分隔线 9 + gap 8
  + 应用芯片 180（长应用名，max-width 220）+ gap 8 + 返回 28
  ≈ 637px   （macOS）
  + Windows 窗口按钮 84 + gap 8 = 729px   ← 已经超过 720
```

也就是说**在加任何东西之前**，「Windows + 最小窗口 + 长应用名 + 周粒度」这个组合就已经
溢出了。再塞进时间线那两个按钮（重置视图 ≈ 80 + 展开空白 ≈ 92 + gap 16 ≈ 188px），
缺口是 macOS 约 105px、Windows 约 189px。

> 顶栏现有的 `@media (max-width: 940px)` / `(max-width: 820px)` 降级是**视口宽度**驱动的，
> 而真正要看的是顶栏自身宽度（= 视口 − 240）。这两条媒体查询保留不动（它们负责固定区的
> 收缩），工具区的降级由本单新组件用 `ResizeObserver` 做**真实测量**，两者不冲突。

**结论：工具区必须自己测量、自己降级。这不是防御性设计，是必需品。**

## 4. 总体设计

### 4.1 架构：工具注册表，不是把状态搬进 store

```
App.tsx
└─ <TopBarToolsProvider>          ← 必须同时包住 TopBar 和 <main>
     ├─ <TopBar>
     │     └─ <TopBarTools />     ← 消费方：测量宽度、分配可见/溢出、渲染 ⋯ 菜单
     └─ <main> → 页面
           └─ useTopBarTools([...], deps)   ← 生产方：页面仍然持有自己的状态
```

**为什么不把 `compressed` / `layoutId` / `viewport` 搬进 `store/context`：**
卡在 `resetView`。它不是状态，是**对图表的命令式操作**（重置 viewport 需要 Timeline 内部的
虚拟坐标模型 `segmentsData.totalVirt`）。把回调塞进全局 store 是用最丑的方式实现了注册表。
页面继续持有状态，只把**渲染好的节点**注册上去，Timeline 不必对外暴露内部模型。

### 4.2 工具区的两个来源

`TopBarTools` 渲染的项来自**两处**，拼成一个数组一起参与宽度分配：

1. **内建上下文芯片**（`TopBarTools` 自己从 store 读，页面不用管）：
   - `page === "timeline" && focusHour !== null` → `定位 · 14:00` 可清除芯片
   - `page === "input" && selectedKey !== null` → `单键 · A` 可清除芯片
   - 这两项恒为 `priority: "high"`
2. **页面注册项**（`useTopBarTools`）

这样注册表保持**单生产者**（只有当前页面写），不会出现 TopBar 和页面互相覆盖的竞态。

### 4.3 降级策略：溢出菜单「⋯」，不是横向翻页

装得下 → 全部平铺，**不显示任何多余 chrome**。
装不下 → 保留高优先级项，其余收进一个 24×24 的「⋯」按钮，点开是竖排菜单。

```
┌─────────────────────────────────────────────┐
│ 日 周 月  ‹ 8月19日 周三 ›  今天 │ Chrome ▾    │
│                      ⟨重置视图⟩ ⟨⋯⟩   ←  ⎕ ✕ │
└─────────────────────────────────────────────┘
              点 ⋯ 展开：
                   ┌──────────────┐
                   │ ⤢ 展开空白    │
                   └──────────────┘
```

选它不选横向翻页的理由：当前每页工具只有 1–3 个，翻页箭头本身要吃 56px（等于为了省 80px
先花 56px），且用户看不见第二页有什么。「⋯」只吃 28px，点开即见全部。

## 5. 阶段 1 · 建机制（空载接入，不搬任何控件）

### 5.1 新建 `src/components/topbar/TopBarToolsContext.tsx`

```ts
export type TopBarToolItem = {
  /** 稳定的唯一标识，用于 React key 与宽度缓存 */
  key: string;
  node: ReactNode;
  /** high = 宽度紧张时优先保持可见（筛选态芯片、降级警示）。默认 "normal" */
  priority?: "high" | "normal";
};
```

导出三样：

- `TopBarToolsProvider`：内部 `useState<TopBarToolItem[]>([])`，通过两个 context 分发
  （**读 items 的 context 和写 setItems 的 context 分开**，否则 TopBar 每次工具变化都会
  连带触发页面重渲染）。
- `useTopBarToolItems()`：供 `TopBarTools` 读。
- `useTopBarTools(items, deps)`：供页面注册。

`useTopBarTools` 的实现必须是：

```ts
export function useTopBarTools(items: TopBarToolItem[], deps: DependencyList) {
  const setItems = useTopBarToolsSetter();
  useEffect(() => {
    setItems(items);
    return () => setItems([]);
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, deps);
}
```

> ⚠️ **必须在 `useEffect` 里 `setItems`，绝不能在 render 期间调用。**
> ⚠️ **依赖数组必须由调用方显式传入，绝不能把 `items` 本身放进 deps** ——
> `items` 里含 JSX，每次 render 都是新引用，放进 deps 就是无限重渲染。
> 把这两条警告原样写进 `useTopBarTools` 的 JSDoc 注释里。

### 5.3 新建 `src/components/topbar/TopBarTools.tsx`

渲染结构：

```tsx
<div className="topbar__tools" ref={containerRef}>
  {/* 常驻离屏测量层：渲染全量项，只用来读宽度，不可见不可点 */}
  <div className="topbar__tools-measure" aria-hidden ref={measureRef}>
    {allItems.map(it => (
      <div className="topbar__tools-item" key={it.key} data-key={it.key}>{it.node}</div>
    ))}
  </div>

  {visibleItems.map(it => (
    <div className="topbar__tools-item" key={it.key}>{it.node}</div>
  ))}

  {overflowItems.length > 0 && (
    <button className="topbar__tools-more" data-tauri-drag-region="false" …>⋯</button>
  )}

  {menuOpen && overflowItems.length > 0 && (
    <div className="topbar__tools-menu" data-tauri-drag-region="false">
      {overflowItems.map(it => (
        <div className="topbar__tools-menu-row" key={it.key}>{it.node}</div>
      ))}
    </div>
  )}
</div>
```

**测量与分配算法：**

1. 离屏测量层**常驻渲染全量项**，样式 `position:absolute; visibility:hidden;
   pointer-events:none; white-space:nowrap; left:0; top:0;`。
   从它的子元素读 `offsetWidth`，得到 `key → width` 映射。
   —— 这样避免「先全渲染一帧再收起」造成的闪烁。
2. 用 `ResizeObserver` 同时监听：
   - `containerRef`（可用宽度变化）
   - `measureRef`（内容宽度变化，比如应用名变长、`14:00` 变 `9:00`）
3. 分配：
   - 排序键 = `priority`（`high` 在前）+ **原注册顺序**（同优先级内保持稳定，用 index 做 tiebreak）
   - 贪心累加 `width + gap`；若存在放不下的项，则先从预算里扣掉「⋯」按钮 24px + 一个 gap，再重算一遍
   - 产出 `visibleKeys` / `overflowKeys`
4. **渲染可见项时必须按原注册顺序输出，不能按排序后的顺序** —— 否则控件会左右跳位置。
5. 全部装得下时：不渲染「⋯」按钮，不产生额外 gap。
6. 项数为 0 时：`.topbar__tools` 宽度为 0，且**不能产生 gap**（见 5.4 的 `:empty` 处理）。

**菜单交互**：直接抄 `TopBar.tsx:97-113` 现成的写法 —— `document` 上挂 `mousedown`
点外关闭 + `keydown` 的 `Escape` 关闭，`useEffect` 里记得移除监听。

**溢出菜单里直接渲染 `item.node` 本身**（竖排），不做第二套 label/icon 逻辑。

## 9. 已知的坑（这 5 条会让你返工）

1. **`.topbar > * { flex: none }` 的权重**（topbar.css:22）。工具区规则必须写成
   `.topbar > .topbar__tools`，否则 `flex: 0 1 auto` 不生效，工具区不会收缩，
   顶栏直接被撑爆。

2. **`useTopBarTools` 的依赖数组**。`items` 含 JSX，每次 render 都是新引用。
   必须显式传 deps，且 deps 里只放**标量**（`viewport !== null` 而不是 `viewport`、
   `layoutName` 而不是整个 layout 对象）。写错的症状是页面卡死或顶栏疯狂闪烁。

3. **测量层不能参与动画**。`.topbar__tools-measure` 里的项要排除 `topbar-tool-in`
   动画，动画期间 `opacity` 变化虽不影响 `offsetWidth`，但如果你顺手加了 transform
   或宽度动画就会污染测量。

4. **可见项要按原注册顺序渲染**。分配算法内部按 priority 排序，但输出时必须还原
   注册顺序，否则宽度一变控件就左右跳位置。

5. **`fill` + `--no-header` 是新组合**。`page-shell.css` 里这两条分支从来没同时生效过
   （Timeline 一直有 header）。阶段 2 必须专门验一次 `.swimlane-body` 的高度和滚动，
   不能只看截图。
