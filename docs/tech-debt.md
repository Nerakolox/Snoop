## 概览页 KPI 标签与口径不符（口径统一的前置项）

- **现状**：`src/pages/Overview.tsx:203` 的 KPI 标签写着「活跃时长」，实际算的是
  `unionDurationMs` = **前台墙钟**（不筛输入，鼠标不动、人不在也算）。与「报告页」定义的
  「活跃时长 = 有输入口径」同名异义。
- **影响**：报告页（批次 4a）上线后，同一天会在概览看到「Chrome 6h」、在报告里看到
  「Chrome 3h20m」，同一个词「活跃时长」指向两个口径，用户会困惑。
- **建议修法**：概览那个 KPI 改名「前台时长」；「活跃时长」一词固定给「有输入」口径
  （报告页的定义）。这样两处数字各得一个诚实的名字。
- **优先级**：报告页上线后**必须处理**，否则两个页面用同一个词指两个数。
- **来源**：批次 4a（报告页 + 日报）。

## 侧栏猫无法区分「人不在」与「人在但无键鼠输入」

- **现状**：侧栏猫把两种完全不同的情况都算成「挂机中」——近 2 分钟没有桶（人离开了
  电脑）vs 有桶但 EPM ≤ 0（人在，但在开会/读文档/看视频）。数据上其实可区分：前者
  `recent.length === 0`，后者有桶但 EPM ≤ 0（`SidebarLive.tsx:28-41` → `computeIntensity`
  `intensity.ts:126-137`）。
- **影响**：0 档文案对后一种情况说错话——人就在屏幕前，猫却说「静悄悄，去哪了喵？」。
  这与报告页「不把无输入时间说成负面」是同一条原则，只是侧栏还没落实。
- **建议修法**：侧栏状态从单一 `intensity` 扩成 `(intensity, presence)` 二元，
  presence 区分 away / present-silent，0 档文案按 presence 分两组。
- **优先级**：低，但如果以后有人反馈「猫说话不对劲」，这是原因。
- **来源**：批次 5（猫的嘴替）。

## 分类占比口径分歧（概览前台 vs 报告有输入）

- **现状**：同一个「分类占比」，两处算法口径不同——概览页走 `app_classify/commands.rs:174`
  的 `SUM(duration_ms)`（前台墙钟，不筛输入）；报告页走 `report/common.rs:361` 的
  `is_active()` 过滤（有输入）。同一分类（如「浏览器」）在两页会得出两个占比。
- **影响**：数值对不上，用户若对照两页会困惑。本次「统一时长口径命名」已做缓解——
  概览分类占比标题旁加「按前台时长统计」、报告分类占比标题旁加「按活跃时长统计」，
  用说明文字兜底，但根因（两处算法不同）仍在。
- **建议修法**：长期统一为同一口径。倾向把概览分类占比也改成有输入口径（与报告、KPI
  语义一致），或反过来统一为前台口径；改一处 SQL/过滤即可，但需同步两页标题旁的说明。
- **优先级**：低（已有说明文字兜底，用户不深究不会察觉）。
- **来源**：统一时长口径命名（小批次，拍板点 1）。

## 报告导出走 SVG foreignObject，平台原生截图是退路

- **现状**：报告导出成图（批次 7）用的是**前端自截图**——SVG `<foreignObject>` 包真实 DOM
  → `<canvas>` → PNG 字节 → Rust 写盘（`src/report/export.ts` 的 `captureNodeAsPng`）。
  当时「Rust 开隐藏窗口 + 截图」的原方案走不通：实测 `tauri-2.11.5` / `wry-0.55.1` 源码里
  `screenshot`/`capture`/`snapshot`/`print-to-image` 全部 0 命中；官方 `tauri-plugin-screenshot`
  是新依赖且只截整屏、不支持隐藏窗口。
- **影响**：foreignObject 的渲染保真度依赖 WebView 的实现细节，跨平台/跨版本可能有差异
  （如 `-webkit-line-clamp`、`box-shadow`、复杂字体排版在截图里表现不一致）。本批已用
  「只用安全 CSS 特性 + 方版叙事改字符截断」提前规避，但**没有双平台运行时真机验证**——
  若某个平台 WebView 的 foreignObject 实现有 bug，导出的图会缺样式或走样，且难以在
  编译期发现。
- **建议修法**：若真遇到保真度问题，退路是**平台原生截图**：Windows 用
  `ICoreWebView2::CapturePreview`、macOS 用 `WKWebView.takeSnapshotWithConfiguration:`。
  这需要把 `wry` 提为直接依赖、写两套平台代码（并具备双平台运行时验证条件）——
  正是本批**主动避开**的路径（之前在 macOS 的 CFRunLoop / Keychain 上栽过）。只有 foreignObject
  方案确实跑不通、且具备验证条件时，才值得回头走这条路。
- **优先级**：低（foreignObject 是确定性机制，当前未发现问题；仅作保真度出问题时的退路）。
- **来源**：批次 7（报告导出成图，方案拍板点：Option C 被否决，A 落地）。
