## Task 1 · 日报数据算法（纯计算，不碰 AI）

**commit**：`feat(report): 日报数据算法 —— 活跃时长口径 + 专注段 + 对比`

**文件**：`src-tauri/src/report/mod.rs`（模块入口 re-export）+ `src-tauri/src/report/daily.rs`（计算）。
`lib.rs` 加 `mod report;`。本 task 无命令消费者，加 `#![allow(dead_code)]` 并配 `#[cfg(test)]` 单测
（参考 `app_classify` 模块的做法）。

**核心结构体**（`#[derive(Serialize, Deserialize, Clone)]`）：

```rust
pub struct DailyReport {
  pub date: String,                 // 'YYYY-MM-DD' 本地日
  // 总览
  pub active_ms: i64,               // 有输入桶时长（主体口径）
  pub foreground_ms: i64,           // 前台墙钟（仅副行展示）
  pub switch_count: u32,            // 派生：桶按时间排序后 bundle_id 变化次数
  pub span_start_ms: i64,           // 首桶 bucket_start
  pub span_end_ms: i64,             // 末桶 bucket_start + duration_ms
  // 排行
  pub top_apps: Vec<AppRank>,       // {name, bundle_id, active_ms, share_pct} Top5 降序
  pub categories: Vec<CategoryShare>, // {category, active_ms, share_pct} 降序
  // 节奏
  pub hourly: Vec<HourCell>,        // 24 个 {hour, active_ms}（有输入口径）
  pub peak_hour: u8,                // active_ms 最大的小时
  pub longest_focus: FocusSegment,  // {start_ms, end_ms, duration_ms}
  // 对比
  pub vs_7d: Compare7d,             // {avg_active_ms, avg_switch_count, active_delta_pct, switch_delta_pct}
  pub new_apps: Vec<AppRef>,        // {name, bundle_id}：今天有、此前30天未见
}
```

**入口函数** `compute_daily_report(conn: &Connection, date: &str) -> Result<DailyReport, String>`，四步：

1. `query_day_buckets(conn, date)`：`SELECT ... FROM activity_buckets WHERE date(bucket_start/1000,'unixepoch','localtime') = ?1 ORDER BY bucket_start`。用于切分活跃/前台、app 聚合、切换次数、专注段、跨度。
2. `query_hourly_active(conn, date)`：`GROUP BY strftime('%H', datetime(bucket_start/1000,'unixepoch','localtime'))`，WHERE 带「有输入谓词」，`SUM(duration_ms)`。补齐 24 格，`peak_hour` = argmax。
3. `query_buckets_range(conn, date-7, date)`：近 7 天（不含当天）原始桶，用同一套「活跃聚合 + 切换计数」helper 算均值。**分母 = 有数据的天数**（不是 7，沿用前端 `daysWithDataOf` 语义）。
4. `query_distinct_apps(conn, date-30, date)`：前 30 天出现的 `app_bundle_id` 集合；当天桶的 bundle_id 做差集 → `new_apps`。

**必须写进注释的两处概念 + 一处取舍**：

- **专注段**（定义 + 理由）：
  > 专注段 = 在「活跃桶」（有输入桶）序列上，把相邻活跃桶之间时间间隙 ≤ 5 分钟的连成一段；跨应用算同一段。
  > - 间隙取 5 分钟：桶是 5 秒级，读文档/思考的输入停顿通常 < 5 分钟；起身离开（喝水/走动/锁屏）通常 ≥ 5 分钟。5 分钟是「离开」的常用启发式阈值，也天然避开系统挂起边界。
  > - 跨应用算同一段：专注衡量「人是否持续投入」，不是「是否盯着同一窗口」。VS Code ↔ 终端 ↔ 浏览器查资料之间的快速切换正是深度工作的表现；打断专注的是「人离开」，不是换应用。
  > - 基于活跃桶：挂机桶（如 IDM 前台无输入）不会延长专注段，和活跃口径同一个根子。
  > - 算法：活跃桶按 `bucket_start` 排序，游标扫一遍，`next.bucket_start - prev.bucket_start > 5min` 断段；最长段 `end - start`。5 分钟做成具名常量。

- **活跃口径**（有输入桶判定，含 `mouse_move_dist` 取舍）：
  > 「有输入桶」判定式见「全局约束」。`mouse_move_dist`（纯鼠标位移）故意不计入：它是连续信号，
  > 若计入，挂着个抖动的鼠标 / 看网页时随手晃鼠标都会被当成「活跃」，挂机判定就失效了。
  > 代价是「只移动鼠标不点击」被算成无输入——数据上是对的，但若占比很高，活跃时长会低于直觉。
  > 若日后用户反馈「活跃时长偏低」，从这里的判定式开始排查。

**单测**（7 条，前 4 条覆盖主路径，后 3 条覆盖边界）：

1. 纯挂机桶不计入 `active_ms`，只计入 `foreground_ms`。
2. 专注段跨应用合并（VS Code ↔ 终端无间隙 → 一段）。
3. 间隙 > 5 分钟断段。
4. 切换次数只数 `bundle_id` 变化（同 app 的 5s 连续桶不计数）。
5. **空数据**：那天完全没有桶 → 不 panic，返回全零结构。
6. **单桶**：只有一条记录 → 专注段 = 那一条；`vs_7d` 分母为 0 时**不除零**（返回 0 / 空）。
7. **跨午夜**：一个桶 `bucket_start` 在 23:59、`duration_ms` 跨过 0 点 → 确认**按起点归属当天**、
   不会被重复计入两天。现有 SQL（`date(bucket_start/1000,...)`）就是按起点归属的，确认这是有意为之，
   并把这一点写进 `compute_daily_report` 的注释。

## Task 2 · 报告存储与生成时机

**commit**：`feat(report): 日报存储与生成时机 —— 每日首次启动生成昨日`

**建表**（`db.rs` 的 `init_schema` 里加，走 `CREATE TABLE IF NOT EXISTS`，与现有迁移风格一致）：

```sql
CREATE TABLE IF NOT EXISTS daily_reports (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  report_date       TEXT NOT NULL,           -- 'YYYY-MM-DD' 本地日
  report_type       TEXT NOT NULL DEFAULT 'day',
  status            TEXT NOT NULL DEFAULT 'ok',  -- 'ok' | 'too_little'
  generated_at_ms   INTEGER NOT NULL,
  active_ms         INTEGER NOT NULL,        -- 反规范化，列表直接读，不 parse JSON
  foreground_ms     INTEGER NOT NULL,
  data_json         TEXT NOT NULL,           -- DailyReport 全量
  narrative         TEXT,                    -- AI 或模板文案（too_little 为 NULL）
  narrative_source  TEXT,                    -- 'ai' | 'template'（too_little 为 NULL）
  UNIQUE(report_date, report_type)
);
```

**store**：`src-tauri/src/report/store.rs`，提供 `upsert`（INSERT ... ON CONFLICT(report_date,report_type) DO UPDATE）、`exists(date,type)`、`get(date,type)`、`list()`。

**生成时机**：在 `lib.rs` setup 里（`app.manage(ai_state)` 与 `app.manage(DbPath)` 之后），
`tauri::async_runtime::spawn` 一个后台任务（参考现有 classify 轮询的 spawn 写法）。流程：

1. `yday = SELECT date('now','localtime','-1 day')`。
2. `exists(yday, 'day')` 为真 → 直接返回（同一天只生成一次）。
3. `compute_daily_report(yday)`：
   - `foreground_ms == 0`（当天 0 桶，等于没采集）→ **不落任何行**，直接返回（「无记录」）。
   - `0 < active_ms < 30*60*1000`（有数据但不足 30 分钟）→ **落一行 `status='too_little'`**：
     存 date + status + active_ms/foreground_ms + data_json（已算好的数字），`narrative = NULL`。
     **不调 AI。**
   - `active_ms >= 30*60*1000` → 走 Task 3 生成文案，落一行 `status='ok'`。
4. `upsert` 落库。

**「记录太少」的三档语义**（写进 store 注释）：
- `foreground_ms == 0` → 「无记录」，完全不落行、列表不显示。
- `0 < active_ms < 30min` → 「记录太少」，落 `status='too_little'` 行，列表显示灰色条目。
- `active_ms >= 30min` → 正常报告，落 `status='ok'` 行。

**手动重新生成**：Task 4 的 `regenerate_report` 命令走同一条「compute + narrative + upsert」路径
（重算重调 AI）。对 `too_little` 日期重算仍是 `too_little`（不足 30 分钟不会凭空变满）。

**已知边界（备注，本批不处理）**：生成只针对「昨天」。若用户某天没打开应用，那天的报告不会生成，
时间轴会留下缺口。「记录太少」无 AI 成本、回填很便宜，但「回填上次生成之后所有缺失日」属于生成
策略变更，**本批不做**，等用户反馈缺口再议。

## Task 3 · AI 叙事（`featureId = ai.daily-report`，已注册 T2）

**commit**：`feat(report): 日报 AI 叙事 —— 事实已定 LLM 只措辞 + 本地模板兜底`

**文件**：`src-tauri/src/report/narrative.rs`。函数签名对齐 classify 的调用方式：

```rust
pub async fn generate_narrative(
  config: &AiConfigState,
  code_map: &Mutex<AiCodeMap>,
  db_path: &Path,
  facts: &DailyReport,
) -> (String, String)  // (文案, "ai" | "template")
```

**payload 契约**（严格遵守信封层「应用名只能在 `apps` 数组里」的规则）：

```json
{
  "system_prompt": "<见下>",
  "facts": {
    "date": "8月20日",
    "active_minutes": 488,
    "switch_count": 87,
    "top_apps": [ {"app":"App A","minutes":180,"share_pct":44}, ... ],
    "categories": [ {"category":"开发","share_pct":61}, ... ],
    "peak_hour": 14,
    "longest_focus_minutes": 96,
    "vs_7d": {"active_delta_pct": 12, "switch_delta_pct": -5},
    "new_apps": ["App D"]
  },
  "apps": [ {"id":"com.google.Chrome","name":"Chrome","windows":[]}, ... ]
}
```

- `facts` 里的数字**全部由 Rust 算好**；应用引用用**稳定代号**（`code_map.ensure_code(id)` 得到 "App A"），
  `apps` 数组提供 id+name 让信封层回映。分类名用 `Category::label()` 的中文名（开发/沟通…），
  那是固定 11 类 taxonom、非应用名，可放 `facts`。
- 走 `envelope::call_ai(config, code_map, db_path, "ai.daily-report", payload, false)`（`json_mode=false`，叙事是纯文本）。
- 失败 / tier 不足 / 功能关闭（`result.ok == false`）→ 落到模板，`source = "template"`。
  **图表数据永远本地算好，AI 只决定叙事文案**（降级契约）。

**system prompt 草案**（含全部禁令）：

> 你是 Snoop 里的猫，陪用户回顾一天。facts 是已经算好的确定事实，数字全部正确。你的唯一任务是把它组织成 100–150 字的中文叙事，语气是陪伴、观察，不是监工、不是绩效报告。
> 禁止：自己计算、推断或改写任何数字；编造 facts 里没有的事实；评判用户（不说「效率低」「浪费时间」「摸鱼」「发呆」「浪费」）；把「前台无输入的时间」说成负面（它可能是开会、阅读、看视频、思考）；提到窗口标题。
> 输出一段纯文本，不要标题、列表、emoji。

**模板兜底**（可读、非流水账，配 1–2 个分支：数据少时降级成更短一句）：

> 今天你活跃了 8 小时 8 分，在 {top1} 待得最久（占 {pct}%），之后是 {top2}。{peak_hour}:00 前后最有干劲，最长一口气专注了 {focus_min} 分钟。{对比句：比最近一周平均多/少 {x}%。}

## 验收边界

- 4 个 commit，各自 `cargo check` 通过、前端 build 通过。
- 生成路径：昨日 0 桶 → 无行；0<活跃<30min → `too_little` 灰色行（不调 AI）；≥30min → `ok` 行
  （AI 可用走 ai、不可用走 template），图表照常。
- 同一词「活跃时长」在报告内只指「有输入」；概览/规律页本批不动。
- `mouse_move_dist` 不计入活跃、`SUM(duration_ms)` 等价 `unionDurationMs` 这两个结论，在注释里写清理由。
