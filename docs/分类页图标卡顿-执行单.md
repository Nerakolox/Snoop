# 分类页卡顿 · 执行单（图标缓存 1024px → 128px）

> 目标：消除分类页「奇卡无比」的持续卡顿。根因是图标缓存里存的是 1024×1024 原图，
> 分类页是所有页面里唯一会一次铺出全部 App 图标的页面（分类柜 ≈90 个 `<img>`，
> 列表 96 行），每个 `<img>` 解码后是 4 MB 位图，浏览器图像缓存被挤爆后每次重绘
> 都要重新光栅化。
>
> 核准日期：2026-11-06。以下现状都已 read / 实测核实。**本单只改图标尺寸，不做别的。**

---

## 零、已核准的事实

### 0.1 磁盘缓存里的图标全是 1024×1024

```
~/Library/Application Support/org.feedra.snoop/icon_cache
  92 个 PNG，全部 1024×1024，共 99 MB，中位数 1.3 MB，最大 2.8 MB
~/Library/Application Support/org.feedra.snoop.dev/icon_cache
  30 个 PNG，全部 1024×1024，共 36 MB，中位数 1.27 MB
```

### 0.2 为什么是 1024

`src-tauri/src/icon_cache.rs:275-280` 的 macOS 提取分支：

```rust
            // 设置目标像素尺寸（NSImage 是矢量+多分辨率，指定 size 后 TIFFRepresentation 才有一致输出）
            use cocoa::foundation::NSSize;
            let target: NSSize = NSSize::new(128.0, 128.0);
            let _: () = msg_send![icon, setSize: target];

            let tiff_data: id = msg_send![icon, TIFFRepresentation];
```

注释的假设不成立：`setSize:` 只改 NSImage 的**逻辑尺寸**，不重采样位图；
`TIFFRepresentation` 仍然按最高分辨率 rep（1024×1024）输出，所以落盘的 PNG 是 1024。

### 0.3 实测卡顿与图标尺寸的因果关系

用真实的 `Categories` / `CategoryCabinet` 组件 + 96 个 App 渲染，只替换图标 payload：

| 图标 payload | 搜索输入中位 | p95 | JS 堆 |
|---|---|---|---|
| 无图标 | 3.0 ms | 8.2 ms | 28 MB |
| 64px 图标 | 2.9 ms | 4.6 ms | 28.8 MB |
| 1024px 图标 | **63.8 ms** | **177 ms** | **348 MB** |

同一份代码、同一份数据，只换图标尺寸，输入延迟差 20–60 倍。列表视图 96 行图标
时堆内存到 1.7 GB。

### 0.4 图标显示尺寸最大只有 30px

全仓 `<AppIcon>` 的 `size` 参数：16 / 18 / 20 / 30（`CategoryCabinet.tsx:904,1216`
是最大的 30）。30px @2x = 60px，128px 源图有充足余量。

### 0.5 已有依赖

`src-tauri/Cargo.toml:33` 已有 `image = "0.25"`，`icon_cache.rs:229`（Windows 分支）
已经在用 `image` 编码 PNG，**不需要新增依赖**。

            Some(png_data) => {

**在 `impl IconCache` 的结束花括号（第 129 行 `}`）之后新增自由函数：**

```rust
/// 把图标 PNG 缩到 `ICON_PX` 以内（**只缩不放**，保持宽高比）。
///
/// macOS 的提取路径先 `NSImage setSize:128×128` 再 `TIFFRepresentation`，但
/// setSize 只改逻辑尺寸、不重采样位图，最终 PNG 仍是 1024×1024。前端最大只显示
/// 30px，分类页一次铺出全部 App 图标时，这些 1024 位图（每张解码后 4 MB）会把
/// 浏览器图像缓存挤爆，导致每次重绘都重新光栅化——实测搜索输入从 3 ms 涨到
/// 60 ms 以上、堆内存涨到 300 MB+。
///
/// 返回 `None` 表示不需要缩（本来就 ≤ ICON_PX）或解码/编码失败，调用方应保留原图。
fn shrink_icon_png(png: &[u8]) -> Option<Vec<u8>> {
    use image::ImageFormat;

    let img = image::load_from_memory_with_format(png, ImageFormat::Png).ok()?;
    if img.width() <= ICON_PX && img.height() <= ICON_PX {
        return None;
    }

    let small = img.thumbnail(ICON_PX, ICON_PX);
    let mut out = Vec::new();
    small
        .write_to(&mut std::io::Cursor::new(&mut out), ImageFormat::Png)
        .ok()?;
    Some(out)
}
```

> `DynamicImage::thumbnail` 会保持宽高比缩到指定框内，不会放大，正是这里要的语义。

### 1.4 启动时清掉旧尺寸的遗留文件（第 26-33 行 `new`）

旧缓存文件名是 `{hash}.png`（无尺寸后缀），不清理会永久占着 ~99 MB 磁盘，
而且会让「验证缓存已全部缩小」的检查产生噪音。

**改前：**

```rust
    pub fn new(cache_dir: PathBuf) -> Self {
        std::fs::create_dir_all(&cache_dir).ok();
        IconCache {
            memory_cache: Mutex::new(HashMap::new()),
            disk_cache_dir: cache_dir,
        }
    }
```

**改后：**

```rust
    pub fn new(cache_dir: PathBuf) -> Self {
        std::fs::create_dir_all(&cache_dir).ok();
        remove_legacy_cache(&cache_dir);
        IconCache {
            memory_cache: Mutex::new(HashMap::new()),
            disk_cache_dir: cache_dir,
        }
    }
```

**在 `shrink_icon_png` 旁边新增：**

```rust
/// 删掉旧版文件名（`{hash}.png`，没有 `_128px` 后缀）留下的图标缓存。
///
/// 旧文件是 1024×1024 原图，新代码永远不会再读它们；留着只是占磁盘。
/// 只删「文件名全是数字 + 扩展名 png」的文件，负缓存 sentinel（`.none`）与
/// 新格式（`{hash}_128px.png`）都不匹配，不会误删。
fn remove_legacy_cache(dir: &Path) {
    let Ok(entries) = std::fs::read_dir(dir) else {
        return;
    };
    for entry in entries.flatten() {
        let path = entry.path();
        if path.extension().and_then(|s| s.to_str()) != Some("png") {
            continue;
        }
        let Some(stem) = path.file_stem().and_then(|s| s.to_str()) else {
            continue;
        };
        if !stem.is_empty() && stem.chars().all(|c| c.is_ascii_digit()) {
            let _ = std::fs::remove_file(&path);
        }
    }
}
```

### 1.5 不需要改的地方

- `extract_icon_png` 的 macOS `setSize` 调用**保留**（无害），真正兜底的是 1.3 的缩小。
- Windows 分支产出 `SHGFI_LARGEICON`（32×32），`thumbnail` 不会放大，行为不变。

## 二、验收

### 2.1 编译

```bash
cd src-tauri && cargo check
```

### 2.2 缓存尺寸

重启 App（dev 构建），进「设置 → 分类」，把分类柜和列表两个视图都点一遍（让图标都被请求过），然后：

```bash
IC="$HOME/Library/Application Support/org.feedra.snoop.dev/icon_cache"
ls "$IC" | head
du -sh "$IC"
for f in "$IC"/*.png; do sips -g pixelWidth -g pixelHeight "$f" | tail -2; done | sort | uniq -c
```

期望：

- 文件名形如 `1234567890_128px.png`，不再有纯数字名。
- 每张 png 的宽、高都 ≤ 128。
- 目录总大小从 ~36 MB 掉到 ~1 MB 量级（30 个应用）。
- 不应该出现 `.none` 文件被误删后重新激增的情况（负缓存本来就该保留）。

### 2.3 交互手感（必须真机 WKWebView，不能只看 Chrome）

在分类页：

1. 分类柜视图，搜索框连续输入 10 个字符——不应再有明显掉帧/输入延迟。
2. 点开两个文件夹浮层，再关闭——不应卡顿。
3. 列表视图，滚动到底、切回分类柜——不应卡顿。
4. 打开开发者工具（dev 构建）在 Console 里看：
   `performance.memory.usedJSHeapSize / 1048576` 应在几十 MB 量级，
   不再随图标数量涨到几百 MB。

### 2.4 回归

- 图标能正常显示（不是空白/首字母占位）。
- 「设置 → 开发者 → 刷新 App 图标」仍能工作，刷新后缓存仍是 128px。
- 没有图标的系统进程仍走负缓存，不会每次重试。
