## 三条跨批语义（写死，任何一批都不得自行解释）

### 1. `adaptKind` 是读取时投影，不写回全局

页面消费 `adaptKind(page, state)` 的返回值即可，**绝不要在 useEffect 里 `setKind`**。否则「概览(月) → 时间线(降级为日) → 返回」回到概览会变成日，用户会觉得应用把他的选择吃掉了。降级必须**可见**（页头挂警示文案），但**不持久**。

### 2. toast 的撤销 = `back()` 整体回退

不是"只清掉某一个字段"。反例：概览点 Chrome 跳时间线，若撤销只清 appId，用户会停在「时间线 + 无筛选」——一个谁都没要求过的状态。

分项清除是 `ContextChips` 上那个叉的职责，两者不重叠。

推论：**只有走了 `actions.navigate()` 的操作才配弹 toast**（因为只有它压了栈）。顶栏上改范围、改筛选不弹 toast。

### 3. store 只存语义，不存毫秒

store 里是 `(kind, anchor)`，各页用 `toMs(kind, anchor)` 自己派生 `[start_ms, end_ms)`。

时间线额外传 `{ liveEnd: true }` 保留它现有的「今天时 end = 当前时刻」语义（原 `Timeline.tsx:123`）。这个规则只属于时间线，不该污染 store。

# Batch 0.5 · 修 key_details 的 N+1（已完成，存档）

## 背景

`src-tauri/src/activity_tracker.rs:21` 的 `MAX_BUCKET_MS = 5000`，桶是 **5 秒粒度**，活跃一天约 5000+ 个桶。

原 `Keyboard.tsx` 的 `loadFilteredData` 在选中具体 App 时，对**每一个桶**串行调用 `get_key_details(bucket_id)`，日范围数千次、周范围上万次串行 IPC。

它没被当成 bug 报出来，是因为 `Keyboard.tsx:144` 的 `refresh()` 里强制 `setAppFilter("all")`——切日/切周/刷新都把 App 选择丢掉，用户很难在这个状态上停留。重构第一件事就是删掉那行（appId 变全局），删掉后地雷起爆。所以必须前置。

## 已完成的改动（`f9a6c8a`）

**后端**
- `get_key_details_in_range` 加 `app_bundle_id: Option<String>`，SQL 用 `(?3 IS NULL OR ab.app_bundle_id = ?3)` 过滤，不动表结构。
- 新增 `get_key_hourly_distribution`（单键按本地整点聚合，时区处理照抄 `get_hourly_activity` 的四步字符串转换）。
- 新增 `get_key_app_distribution`（单键跨 App 聚合，降序）。
- 三者已在 `lib.rs` 的 `generate_handler!` 注册。

**前端**
- `fetchKeyDetailsInRange` 第三参数可选，Dev 页原有单参调用不受影响。
- 新增 `fetchKeyHourlyDistribution` / `fetchKeyAppDistribution` 封装。注意 `keyCode` 类型是 **string**。
- `fetchKeyDetailsOfBucket` 保留（Dev 页展开行还在用）。
- `loadFilteredData` 的逐桶串行循环已删除，两分支合并成一次 `fetchKeyDetailsInRange`。
- `Keyboard.tsx:144` 的 `setAppFilter("all")` **按工单保留**，留给 Batch 4 删。

人工验证通过，响应速度已从数秒级降到即时。

## 盘点后新增的三件事（原方案没有）

### 1. `page` 必须进 store

视图栈的栈项是 `{page, kind, anchor, appId, focusHour, selectedKey}`，`back()` 要能恢复**页面**。而现在 `page` 在 `App.tsx:43` 的 useState 里，store 改不了它，`back()` 就是残废的。

所以 `page` 进 store，App 只保留 `displayed` / `phase` 两个纯动画态，两段式转场（`FADE_OUT_MS=160` → 双 rAF → `FADE_IN_MS=280`）从"点击时触发"改成"监听 `page` 变化时触发"。`handleSelectRef` 可以删掉（actions 引用恒定，不再需要 ref 兜最新回调）。

### 2. 拖拽区是「新增」不是「迁移」

盘点结论：macOS 下右半边窗口**现在完全没有**拖拽区，拖拽全在侧栏（`base.css:188` + `Sidebar.tsx` 各层的 `data-tauri-drag-region`）。

所以顶栏是**新增**拖拽区，**侧栏原有的一律保留不动**。用户已经习惯拖侧栏，动它是纯损失。这条改完，Batch 1 的拖拽风险从"中"降到"低"。

### 3. 预验 `fill` + `--no-header`

`page-shell.css` 里这两个变体**从未同时出现过**（只有 Timeline 用 `fill`、只有 Keyboard 用 `stickyHeader`）。Batch 3 把日期导航搬走后，Timeline 很可能变成这个组合。

Batch 1 里临时试一次并把结论写进 commit message。别留到 Batch 3 那个高风险批次才发现——那时分不清是 PageShell 的锅还是时间线重写的锅。

## 原方案里被推翻的一条

> ~~"若外层用 grid，列定义改 `minmax(0, 1fr)`"~~

本项目外层是 flex（`.app-shell` row + `.app-right` column），没有 grid。`.app-right` 已有 `min-width: 0`，`.sidebar` 是定宽 `flex: 0 0 var(--sidebar-width)`。**横向没有同类问题，跳过这条。** 纵向的 `.app-main { min-height: 0 }` 是真问题，必做。

## 本批边界

# Batch 2 · 概览页接入全局上下文 + 全量下钻

## 盘点后对本批的三处调整

1. **节奏区不再调 `fetchHourlyActivity`。** 它不接 app 参数，有 appId 时直接废掉。改为一律从 `buckets` 分组求强度，新增 `intensityByHourFromBuckets` / `statsByDayFromBuckets` 两个纯函数。好处是有无筛选走同一条路径，不会出现"不筛选时准、筛选后不准"。
2. **活跃时长改用 `unionDurationMs`**（`analytics/aggregate.ts:15`，注释写明是"总时长的权威口径"）。现在概览是逐桶裸加，与 `aggregateByApp` 的并集口径不一致，导致"App 排行各行之和"永远对不上"活跃时长"——而这正是本批要核对的验收项。
3. **周期总结卡挪到 Batch 5。** 原本放本批，但那时 Insights 正在重排，两边文案一次对齐更省事，避免在两个批次里各写一半模板。

## 仍然生效的原始要点

1. Overview 删除 `Overview.tsx:106` 的硬编码 `todayRange()`，改为消费全局 `(kind, anchor, appId)`，走 `useRangeData`。
2. **`Overview.tsx:211` 的 `setInterval(refresh, 30_000)` 加条件**：只有 `kind === 'day'` 且 anchor 是今天时才轮询。看上个月的数据没必要每 30 秒重拉一次。轮询触发时要调 `useRangeData` 的 `invalidate()`，否则会一直读缓存。
3. 页头改造：Overview 现在是 `--no-header` 变体（`Overview.tsx:218` 只传了 className），需要新增 header。标题 + 副标题（`${范围名} · ${天数} 天数据${已筛选后缀}`），`adaptKind` 有 note 时在标题右侧渲染警示，标题下渲染 `<ContextChips show={["app"]} />`。
4. **周期总结卡**从 Insights 迁入。模板参数化，日/周/月都出文案：`${范围}${天数描述}，你活跃了 X，敲下 Y 次按键、点出 Z 次点击，鼠标跑了 W 公里。住得最久的是 <App>（时长）。${判语}`。判语按日均活跃小时数分四档，阈值 9 / 6 / 3。文案沿用现有猫人格口吻。
5. **数字卡可点下钻**：活跃时长 → 时间线；总按键/总点击/鼠标里程 → 输入页。悬停时右上角浮出目标提示。多天范围下活跃时长卡副文案写「日均 X · 分母 N 天」，N 为**有采集数据的天数**（不是自然天数）。
6. **App 排行行可点**：`actions.navigate({ page: 'timeline', appId: 该 App })`——**一次 navigate 同时改两个字段**，不要拆成两步（拆了会压出一个中间态）。已有筛选时非选中行 `opacity: 0.34`（不隐藏）。每行右侧挂 `<DeltaBadge>`。行挂 `.drillable`。
7. **节奏区随粒度换形态**：
   - `day` = 24 格热力条，点 → `navigate({ page:'timeline', focusHour: h })`
   - `week` = 7 天柱状，点 → `navigate({ kind:'day', anchor: 该天 })`
   - `month` = 日历热力，同 week
   - 三种形态共用 `src/analytics/intensity.ts`，**禁止组件内自算归一化**
8. 走了 `navigate` 的跳转弹 toast（撤销 = `back()`）。

## 人工验证

三个粒度各点一遍；anchor 前后翻页数据跟着变；每个可点元素都试；toast 撤销有效；返回按钮能回退；**筛选后概览数字确实变了**——核对分 App 时长之和，不是按比例折算。

## 相对原方案的两处修订

1. **~~「布局改左右两栏，右侧固定 266px」~~ 作废。** 算过几何：104 配列 scale=1 需约 990px，缩到下限 `MIN_SCALE=0.55` 仍需 545px；窗口最小宽 960px 切两栏后键盘只剩约 374px，**会永久带横向滚动条**，而它是这页的主体。加上样式即将整体重构，现在做布局重构是做一遍扔一遍。改为：**键盘继续占满宽，两块新内容进现有的 `.kb-lower-section` 网格**。
