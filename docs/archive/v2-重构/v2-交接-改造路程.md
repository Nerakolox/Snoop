## 二、这次重构在做什么

### 2.1 出发点

重构前的问题：

- 时间状态散落在四个页面各自的控件里（Overview 硬编码今天、Timeline 有 `selectedDate`、Keyboard 有日/周切换、Insights 有 `WeekSelector`），切页即丢失
- App 筛选只有键盘页有，且切时间就被强制重置
- 导航轴是「时间」而不是「维度」，概览与洞察职责重叠
- 页面之间不能下钻，每一块数据都是死的

### 2.2 核心架构决策

**时间与应用筛选提升为全局单一真相**，存在 `src/store/context.tsx`：

```ts
interface ContextState {
  page: NavKey;                // 当前页面（视图栈要能恢复它，所以必须在 store 里）
  kind: 'day' | 'week' | 'month';
  anchor: string;              // 'YYYY-MM-DD' 本地日期
  appId: string | null;        // null = 全部应用
  focusHour: number | null;    // 时间线定位
  selectedKey: string | null;  // 单键下钻
}
```

**为什么是 `(kind, anchor)` 而不是 `'today'|'yesterday'|'week'|'month'` 枚举**：枚举表达不了「下钻到 8 月 3 日」和「翻到上上周」。语义式模型让月历格点击、周柱下钻、任意区间翻页全部自然成立。顶栏据此变成「粒度三段 + anchor 导航」，顺带吸收并删除了 `TimelineHeader` 的日期导航与 `components/insights/WeekSelector.tsx`。

**store 只存语义，不存毫秒。** 各页用 `toMs(kind, anchor)`（`src/data/ranges.ts`）自己派生 `[start_ms, end_ms)`。时间线额外传 `{ liveEnd: true }` 保留它「今天时 end = 当前时刻」的活范围语义。

### Batch 0.5 · 修 key_details 的 N+1（`f9a6c8a`）

**这是盘点意外挖出来的现存 bug，不在原方案里。**

`src-tauri/src/activity_tracker.rs:21` 的 `MAX_BUCKET_MS = 5000` —— 桶是 **5 秒粒度**，活跃一天 5000+ 个桶。而键盘页选中某 App 时，对**每一个桶**串行调 `get_key_details(bucket_id)`，日范围数千次、周范围上万次串行 IPC。

它一直没被当成 bug 报出来，是因为 `Keyboard.tsx` 的 `refresh()` 里有一行强制 `setAppFilter("all")`——切日/切周/刷新都把 App 选择丢掉，用户很难在这个状态上停留。**一个 bug 被另一个 bug 盖住了。** 而重构第一件事就是删掉那行强制重置。

改动：

- `get_key_details_in_range` 加 `app_bundle_id: Option<String>`，SQL 用 `(?3 IS NULL OR ab.app_bundle_id = ?3)`
- 新增 `get_key_hourly_distribution`（单键按本地整点，时区处理照抄 `get_hourly_activity` 的四步字符串转换）
- 新增 `get_key_app_distribution`（单键跨 App，降序）
- 前端删掉逐桶串行循环

**未动表结构，未新增采集。** 响应从数秒级降到即时。

## 四、写死的规则（任何后续改动都不得回退）

### 4.1 三条跨批语义

1. **`adaptKind` 是读取时投影，不写回全局。** 页面消费返回值即可，绝不在 useEffect 里 `setKind`。否则「概览(月) → 时间线(降级为日) → 返回」回到概览会变成日，等于应用吃掉了用户的选择。降级必须**可见**（页头挂警示），但**不持久**。
2. **toast 的撤销 = `back()` 整体回退**，不是只清某个字段。分项清除是 `ContextChips` 上那个叉的职责。推论：**只有走了 `actions.navigate()` 的操作才配弹 toast**（只有它压栈），顶栏上改范围/改筛选不弹。
3. **store 只存语义不存毫秒。** 见 §2.2。

### 4.2 技术约束

- **日期处理**：anchor 是 `'YYYY-MM-DD'` 本地日期串。**禁止 `new Date("2026-08-03")`**（ISO date-only 按 UTC 解析，东八区会漂一天）与 `toISOString()`（同样 UTC）。统一走 `parseAnchor` / `formatAnchor`。
- **深色模式**：`src/main.tsx` 恒会给 `<html>` 设 `data-theme`。新 CSS **只写 `[data-theme="dark"]`**，不要写 `@media (prefers-color-scheme: dark)`——后者在「系统深色 + 用户手选浅色」时会错误命中。`base.css` 里的 media query 是历史写法，不要复制。
- **设计 token**：间距只有 `--space-1/2/3/4/6/8`（4/8/12/16/24/32px），**没有 `--space-5` 和 `--space-7`**。颜色一律走 `tokens.css`。
- **`analytics/intensity.ts` 是强度单一真相。** 禁止在组件里自写 `value / max` 这类线性归一化。
- **键盘缩放机制不得简化**：`KeyboardPanel.tsx` 的 `SCROLLBAR_RESERVE=1` / `SCALE_STEP=0.01` 向下量化 / `SCALE_EPSILON=0.005` 死区 / rAF 合并 / 观测 `.kle-viewport` 读 `clientWidth`（靠 `scrollbar-gutter: stable` 断开反馈环）。这五道都是踩坑修出来的，看起来很像「可以简化」。
- **timeline 样式严格隔离**在 timeline 相关文件内。历史上有过污染导致整站崩坏。
- **PageShell 约定**（见 `CLAUDE.md`）：页面根 class 只放布局，绝不写 padding。
- 不引入新依赖。

### 4.3 全站共享件（在 `src/components/shared/`）

| 组件 | 用途 |
|---|---|
| `ContextChips.tsx` | 页头的可清除上下文标签（应用 / 定位 / 单键） |
| `Toast.tsx` + `useToast()` | 跨页跳转反馈，撤销 = `back()` |
| `drillable.css` | `.drillable` —— 全站「可下钻」的统一悬停导轨，2.5px 紫色 `::before` |
| `DeltaBadge.tsx` | **全站唯一的环比展示**，五态互斥，**单位是分钟** |

`DeltaBadge` 五态：两期都低于阈值 → 灰「—」+ 说明原因；基期不足当期达标 → 「新」；|变化| < 2.5% → 「持平」；涨/跌 → `↑/↓ X.X%` + vsLabel。阈值按粒度：日 20 / 周 120 / 月 600 分钟。

## 五、已知问题与挂账

### 5.1 🔴 当前最要紧：样式崩坏

**现象**：Batch 4 完成后，样式出现严重问题（用户报告「样式完全出问题」）。功能验收通过，问题在视觉层。

**排查线索，按可能性排序：**

**① `.kb-lower-section` 的 `auto-fit` 网格（最可能）**

`src/styles/keyboard.css` 里从

```css
grid-template-columns: minmax(0, 1fr) minmax(0, 1.2fr);   /* 原：2 块，两列 */
```

改成

```css
grid-template-columns: repeat(auto-fit, minmax(240px, 1fr));  /* 现：4 块 */
```

现在这个网格里有**四块**：`MousePanel` / `TopKeysPanel` / `RatioPanel` / `KeyDetailPanel`（`Keyboard.tsx:254-266`）。

在默认窗口 1180px 下估算可用宽：`1180 − 240(侧栏) − 10(gutter) − 64(页面左右) − 48(panel padding) ≈ 818px`。四列时每列 `(818 − 3×32) / 4 = 180px < 240px`，`auto-fit` 会退到三列 `(818 − 64) / 3 ≈ 251px`，**第四块单独换行并被拉满整行宽** —— 一个三窄 + 一宽的不对称布局。这大概率就是「看起来完全乱了」。

**② `scrollbar-gutter: stable` 影响全站**

`src/styles/base.css` 的 `.app-main` 新增了这一行，**所有页面恒定少 10px 可用宽**。若某页原本卡在临界宽度，会被挤出问题。这一行有实际价值（断开键盘缩放的反馈环），删之前先确认替代方案。

**③ 输入页 header 内容大幅变少**

删掉 App 筛选行与日期行后，`stickyHeader` 里只剩配列选择器 + 可能的映射警示。原来的三行样式（`.kb-filters` 的 gap、`.kb-filter-row` 的排布）是按三行调的，现在只剩一行可能显得空或错位。

**建议**：不要单点修补。用户已计划整体样式重构（第六节），把这些当作重构的输入。

## 七、协作方式（这套流程有效，建议延续）

1. **每批开工前先写执行文档**。把要改的现有代码原文抄进去、把易错点写死、给完工检查表。`docs/v2-batch1-地基.md` 是详细度的基准线。
2. **每批切成 3–4 个 commit**，每个 commit 后代码都应该能跑。批次开头先打一个 `chore: Batch N 开工前存档` 作为回滚点。
3. **每批做完停下等人工验证**，不连做。
4. **写代码的模型看不到真实运行效果**（Tauri 原生窗口，无头环境验不了 `invoke`）。所以完工检查表要分「代码层（可自查）」与「功能/平台/主题层（需人工）」两部分。
5. **执行文档与总纲冲突时以执行文档为准**，且发现冲突要**先问再动手**，不要自己发明绕路——Batch 4 里 `KLEKeyboard.tsx` 那次就是正确示范。
6. **原方案（照原型写的）多处与实际代码不符**。动手前一定先读现有实现，Batch 3 因此砍掉三分之二工单，Batch 4 因此推翻了布局方案。
